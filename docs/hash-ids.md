# Hash IDs

[README](../README.md) · [Runtime APIs](runtime.md) · [Numeric types](numeric-types.md)

Hash ID columns expose GraphQL `ID` strings while data sources use database values: `number` for integer IDs and `bigint` for bigint IDs. References use their parent column's encoder, including renamed public fields and referenced primary keys.

## Values and errors

The exported `makeNumberIdEncoder` and `makeBigIntIdEncoder` factories return `HashIdEncoder<number>` and `HashIdEncoder<bigint>` respectively.

| Value | Behavior |
| --- | --- |
| `0` / `0n` | Encoded normally; decoding restores the original numeric type |
| `null` | Preserved by both encode and decode |
| `undefined` | Preserved by both encode and decode |
| Empty, undecodable, or multiple-value Hash ID | Throws `GraphQLError` with message `Invalid Hash ID` and `extensions.code: BAD_USER_INPUT` |
| Negative or non-integer input to encode | Rejected with the same error |
| Unsafe integer for the number encoder | Rejected with the same error, including when decoding |

The number encoder accepts nonnegative safe integers. The bigint encoder accepts nonnegative native `bigint` values. It does not accept numbers or decimal strings in place of bigint. Null and undefined have explicit overloads; decoding a string returns the declared numeric type or throws.

Generated queries and mutations reject undecodable Hash IDs before database operations. Subscription filter IDs are decoded once during subscription setup, before opening the event iterator. Invalid subscription input therefore returns an error immediately rather than silently waiting for events. Required GraphQL arguments still reject missing values or null during GraphQL validation.

A valid Hash ID for a nonexistent row remains a normal lookup: primary queries return null and delete returns false. Hashids encodes identifiers; it does not authenticate requests or authorize row access. A different salt is not a guaranteed security boundary: it can produce an undecodable value or decode to another number.

## Clearing a nullable reference

For a nullable, updatable Hash ID reference called `ownerId`, an update behaves as follows:

| Input | Database effect |
| --- | --- |
| `{ ownerId: encodedId }` | Set the decoded foreign key |
| `{ ownerId: null }` | Set the foreign key to SQL `NULL` |
| `{}` | Keep the current value |
| `{ ownerId: undefined }` in a direct TypeScript call | Keep the current value |

For example, using the names generated by your schema:

```graphql
mutation ClearOwner($id: ID!) {
  updateDocument(document: { docId: $id, ownerId: null }) {
    docId
    ownerId
  }
}
```

GraphQL JSON has no undefined value; omit the field to leave it unchanged. During creation, omitted fields retain the existing database default behavior, while explicit null inserts SQL `NULL` subject to database constraints.

## Generated types and filters

Direct calls to generated GraphQL resolvers take encoded string IDs, just like GraphQL clients. Data-source methods and context-owned fields take database values. Nullable mutation references accept `string | null`; optional input fields can be omitted. Context-owned fields are excluded from the public input type and supplied from server context.

Custom query conditions can declare Hash ID arguments with `Conditions.value.arg(name, 'ID')`. Comparisons and BETWEEN endpoints targeting Hash ID columns decode through the appropriate encoder. Existing `String` arguments for these conditions remain supported. Subscription filters use database column names in their configuration and expose Hash IDs as `ID!` arguments.

A context name shared across mutations is generated once when its TypeScript type agrees. Reusing one name for incompatible types, such as number and bigint, fails generation with a descriptive error.

## Upgrading

Install/build the updated library and run `yarn sasat generate` in your application. Regeneration is required for zero-valued output, nullable mutation decoding, filter validation, and corrected resolver input types. Existing salts and valid encoded IDs remain unchanged.

Custom encoders in application-owned `idEncoder.ts` are preserved. Review them manually: invalid non-null strings should throw rather than return undefined. Generated output and mutation input code bypass custom encoders for null and undefined. Update direct resolver calls that previously passed raw numeric IDs to pass encoded strings, or use data-source methods for database values.
